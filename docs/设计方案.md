## 0. 先看结论

**三项成果是一条链，不是三份独立作业。** 原型产生可测的东西，验证记录证明它有用并据此改过，计划书的每个论点都引用前两者的证据。课件原话是“书面写得再好，没有可用的原型和真实反馈也拿不到高分”，所以资源分配建议为：原型 45%、验证 35%、计划书 20%，计划书主要在第 5 周以后写。

**原型一句话定位：** 粘贴一份招聘信息，调用已保存的个人档案，先追问关键缺失信息，再输出一页报告（规则判定的三档结论、硬门槛逐项检查、逐条对照表、可勾选准备清单），可保存多个岗位并排比较。

|---|---|---|---|

## 1. 三项成果与评分的对应

| 成果 | 课件要求 | 对应“能用、有人用、值得做” | 交付物 |
|---|---|---|---|
| 产品原型 | 用户可以输入需求，完整体验一个核心任务的全过程 | 能用 | 可访问的网页链接；源码；演示视频（防现场断网）；功能测试报告 |
| 用户验证记录 | 展示用户反馈、功能测试，以及据此做出的修改；改进要有依据 | 有人用 | 访谈记录；可用性测试记录；测试集评测结果；修改日志（问题、证据、改动、复测） |
| 创业计划书 | 说明目标客户、产品差异、收费假设和主要成本；收费是待验证的假设 | 值得做 | 计划书正文，每个论点标明证据来源；附成本测算表 |

## 2. 盲区扫描：你们可能还没想到的问题

按严重程度排序。前两条必须先处理。

1. **作业2.docx 里的访谈记录没有标注“模拟”。** 第二周_最终选题设计.md 的附录二明确写着那两份记录是虚构示例，但作业2.docx 里同样的内容以“访谈记录 一、二”出现，没有任何说明。如果这份文件已经交了，建议主动向老师说明这两份是填写示例，并尽快补交真实访谈。不管交没交，验证记录里一律不得引用这两份内容，包括其中“实习时长写着优先其实是硬门槛”这类看起来很有道理的发现；这个点可以作为待验证假设，但要等真实用户说出来才能当证据用。课件第 31 页原话：“AI 可以帮忙整理，但不得虚构用户或访谈内容”。
2. **差异点偏薄，你们自己已经写过。** 实测显示通用大模型能完成要求分级、硬门槛识别和具体建议。所以原型演示和验证的重点不能是“我们能分级”，而是四件通用聊天做不到或做不稳的事：结论口径固定、追问在结论之前、证据可核对（原句真实存在）、多岗位保存对比。验证设计要能直接回答“用户在不在意这四件事”，否则路演时会被问住。
3. **基线对照只测了 Claude。** 目标用户实际用的是 DeepSeek、豆包、Kimi。验证阶段要用用户自己常用的那个模型做对照，否则“比通用聊天强”的说法不成立。
4. **模型输出不稳定会直接毁掉演示。** 需要强制 JSON 输出、程序校验结构、失败自动重试一次；温度设为 0 也不能保证完全一致，要实测。
5. **证据原句可能是编的。** 模型声称“招聘信息原文写了某句话”，这句话可能并不存在。解决办法很简单：程序检查每条引用是否真的是招聘信息文本的子串，不是就标红。这一条同时是很好的演示点和测试指标。
6. **个人信息与隐私。** 档案包含学校、专业、经历，属于个人信息。D3 改为服务器保存后，我们就是这些数据的保管方：注册页要有告知同意，说明存什么、存在哪、给谁看（模型厂商）、怎么删；提供“注销账号并删除全部数据”按钮；档案表单不设姓名、电话、学号字段，测试时也提醒用户不要填；密码只存加盐哈希。接口调用会把内容发给模型厂商，要在页面上写明。计划书的风险章节要提到《个人信息保护法》的告知同意要求。
7. **访问问题。** Streamlit 官方免费托管（streamlit.app）在国内访问不稳定，用户测试时可能打不开。建议部署到国内平台，例如魔搭社区创空间（是否支持 Streamlit 及免费额度需在动手前核实），或者测试时在组员电脑上本地运行、现场试用。
8. **接口密钥泄露。** 密钥只放在平台的密钥配置或本地环境变量里，不写进代码、不传到公开仓库。
9. **招聘信息里的隐含硬门槛。** 届别、城市、到岗天数、实习时长、学历这类条件，即使写着“优先”，也可能实际是硬门槛。第一版的处理是：这五类条件由程序单独检查，写着“优先”的标为“疑似硬门槛，建议先问 HR”，不直接判死。这条处理本身要在用户测试中验证。
10. **第 5 周现场演示风险。** 网络、接口限流、额度用完都可能发生。必须准备录屏和预先跑好的示例报告。
11. **免费托管平台的硬盘可能是临时的。** 平台重启或重新部署时，存在本地的 SQLite 文件会被清空，用户数据全丢。部署前必须确认平台是否提供持久存储；不提供就改用一台云服务器（可查高校学生优惠），或改接外部云数据库。这一条要在第 5 周前试一次重启验证。
12. **服务器在境内时的域名备案。** 境内服务器用域名对外提供网页通常需要 ICP 备案，耗时较长；课程阶段可以直接用 IP 地址加端口访问，或选择境外（如香港）节点。具体以云厂商当前规定为准，部署前核实。

### 3.2 用户流程与页面

整个产品四个页面，侧边栏切换。

```
① 我的档案 ──> ② 分析岗位 ──> ③ 追问（有缺失时才出现）──> ④ 岗位报告
                                                         │
                                                         └──> ⑤ 岗位对比（已分析岗位列表）
```

**① 我的档案**：表单形式，不是自由文本，因为硬门槛检查需要结构化字段。

```
┌ 我的档案 ───────────────────────────────────┐
│ 学历 [本科▼]  专业 [信息管理      ] 专业大类 [管理类▼] │
│ 入学年份 [2024]  预计毕业 [2028]  ← 程序自动核对 │
│ 所在城市 [上海]  可接受城市 [上海, 杭州]       │
│ 学期中每周可到岗 [3] 天  可连续实习 [3] 个月      │
│ 最早到岗日期 [2026-11-01]                    │
│ 技能  Excel [熟练▼]  SQL [会用▼]  Python [没学过▼] [+ 添加] │
│ 经历  [社团招新报名统计：用 Excel 整理 300 条报名… ] [+ 添加] │
│ 证书  [英语六级 已通过▼] [+ 添加]               │
│ [保存档案] [下载档案文件] [上传档案文件] [载入示例档案] │
└────────────────────────────────────────┘
```

技能熟练程度用带锚点的四档，避免“熟悉”“掌握”各说各的：

| 档位 | 定义（会写在下拉框提示里） |
|---|---|
| 没学过 | 没有接触过 |
| 了解 | 上过课或看过教程，没有独立做过东西 |
| 会用 | 独立完成过课程作业或小练习 |
| 熟练 | 在项目、实习或竞赛中实际用过，能说出具体产出 |

**② 分析岗位**：一个大文本框粘贴招聘信息，可选填岗位名称、公司、链接。按“开始分析”。

**③ 追问**：只在硬门槛或核心能力信息不足、或档案自身矛盾时出现，最多 3 个问题，以选择题为主，每题附“为什么问这个”。用户可以跳过，跳过的项在报告里标“信息不足”。

```
┌ 出结论前需要确认 2 件事 ──────────────────────┐
│ 1. 岗位要求每周到岗 4 天，你档案写的是 3 天。    │
│    学期中能否调整到 4 天？                       │
│    ( ) 能  ( ) 不能  ( ) 不确定                  │
│    为什么问：这是硬门槛，直接决定结论档位。      │
│ 2. 你的 SQL 是否在课程项目以外独立写过查询？     │
│    ( ) 写过，做过……[补充一句]  ( ) 没有           │
│ [提交并出报告]  [跳过，直接出报告]               │
└────────────────────────────────────────┘
```

**④ 岗位报告**：一屏能看完，自上而下是结论、硬门槛、对照表、清单。

```
┌ 数据分析实习生｜某公司 ─────────────────────────┐
│ 结论：谨慎投递                                   │
│ 原因：硬门槛“每周到岗 4 天”不满足（你：3 天）。     │
│ 补救：投递前先问 HR 能否接受 3 天；能，则升为“补充后投递”。│
├ 硬门槛检查 ──────────────────────────────────┤
│ ✓ 学历 本科      ✓ 届别 2028 届                │
│ ✗ 到岗 4 天/周    ✓ 实习时长 ≥3 个月  ✓ 城市 上海     │
├ 逐条对照 ──────────────────────────────────┤
│ 级别   要求（原文）        你的情况（档案原句）   判断   │
│ 核心   掌握 SQL            SQL：会用（课程作业）  部分符合│
│ 核心   熟练使用 Excel      Excel：熟练（社团统计）符合   │
│ 加分   了解 Python 者优先  Python：没学过         不符合 │
│ ⚠ 引用核对失败的行标红                            │
├ 投递前准备清单 ─────────────────────────────┤
│ [ ] 简历把“社团统计”改写为：用 Excel 透视表整理 300 条…  │
│ [ ] 补一个 SQL 小项目：……                        │
│ [ ] 面试准备：“你用 SQL 解决过什么问题”             │
│ [导出报告]  [保存到岗位列表]                      │
└────────────────────────────────────────┘
```

**⑤ 岗位对比**：表格列出已分析岗位：岗位、公司、结论、未满足硬门槛数、核心能力缺口数、待办清单完成数。可勾选两个岗位并排看。这一页是“通用聊天做不了”的最直观证据，第一版做最简单的表格即可。

D3 落地方案（2026-10-12 修订为服务器存储）：

| 方面 | 做法 | 理由 |
|---|---|---|
| 数据库 | 线上用 Supabase 免费版（云端 PostgreSQL 数据库），本机开发和测试用 SQLite；代码统一用 Streamlit 自带的 st.connection("sql") 访问，切换只改密钥配置里的连接地址。四张表：users、profiles、reports、applications；档案和报告整体存成文本形式的 JSON，只用两种数据库都支持的基础 SQL | 2026-10-12 决定全部用免费服务；免费网页托管平台的硬盘是临时的，数据必须放在外部数据库 |
| 登录 | 用户名 + 密码，密码用 Python 自带的 hashlib.scrypt 加盐哈希；登录状态放在 Streamlit 会话里 | 不引入第三方登录库；不收手机号和邮箱，减少个人信息 |
| 邀请码 | 注册需要邀请码，由组内发给测试者 | 防止陌生人刷接口额度；也便于统计测试者来源 |
| 次数上限 | 每人每日分析次数上限（初定 10 次，写在配置里） | 控制接口费用；同时是“免费额度 + 付费”收费假设的雏形 |
| 找回密码 | 第一版不做，注册页提示“忘记密码无法找回，请记好” | 找回密码需要邮箱或手机，与少收个人信息冲突 |
| 删除 | “注销账号”一键删除该用户全部记录 | 个人信息保护法要求可删除 |
| 部署 | 网页放魔搭社区创空间（国内平台，免费）；数据库放 Supabase 免费版，区域选新加坡或东京。用户浏览器只连魔搭，魔搭服务器再连 Supabase 和 DeepSeek | 国内同学能打开网页；数据库不受托管平台重启影响 |
| 免费版限制 | Supabase 免费项目 500 MB 数据库、最多 2 个活跃项目，连续一周没有访问会自动暂停，需手动恢复（据 supabase.com/pricing，2026-10-12 查询） | 课程规模用不完 500 MB；测试期每天有人用不会暂停，假期前后要留意 |
| 待核实 | 魔搭创空间是否支持 Streamlit（第三方资料称支持，未见官方文档）、空闲时是否休眠、能否访问境外数据库 | 第 5 周前先部署一个只有一行字的测试页验证；不行的备选是 Streamlit 官方免费托管（国内访问不稳定） |

数据访问全部经过 storage.py 里的几个函数（读写档案、报告、投递记录、用户），其他文件不直接写 SQL。

### 3.4 结论判定规则（程序执行，不交给模型）

按顺序判定，命中即停：

| 顺序 | 条件 | 结论 | 必附内容 |
|---|---|---|---|
| 1 | 任一硬门槛“不符合” | 谨慎投递 | 是哪条、差多少、可行的补救（如先问 HR） |
| 2 | 任一硬门槛“信息不足”（用户跳过了追问） | 补充后投递 | 提示先确认该条 |
| 3 | 核心能力中有任一“不符合”，或“部分符合”达到 2 条 | 补充后投递 | 列出缺口和准备清单 |
| 4 | 其余情况 | 建议投递 | 仍给出准备清单 |

说明：

- 加分项和软性要求不影响档位，只进准备清单。这正好回应“知道哪些可以不满足就敢投”这类诉求（是否真有这类诉求待真实访谈确认）。
- D2 已定严格版（2026-10-12）。第二周的“核心能力缺失超过一半才封顶”已被规则 3 覆盖，不再单列。严格版下两条核心要求缺一条判“补充后投递”。
- 所有阈值写在一个配置文件里，用测试集的人工标注结论来调，不靠拍脑袋。
- “谨慎投递”的措辞一律附补救建议，避免劝退。

五类硬门槛的程序检查：

| 类型 | 档案字段 | 判定方法 |
|---|---|---|
| 学历 | degree | 学历等级比较 |
| 届别 | grad_year | 与要求届别相等；另检查 enroll_year + 4 是否等于 grad_year，不等则在追问中提示矛盾 |
| 城市 | accept_cities | 工作城市是否在可接受列表；远程岗位跳过 |
| 到岗天数 | days_per_week | 大于等于要求天数 |
| 实习时长 | months_available | 大于等于要求月数 |

证书（如证券从业资格）区分“已通过、在考、未考”，归为核心能力由模型判，不进程序检查，第一版先这样。

### 3.5 AI 工作流

固定工作流，两次模型调用加程序逻辑，符合课件“任务步骤固定就用工作流”的建议。

| 步骤 | 执行者 | 输入 | 输出 |
|---|---|---|---|
| 1 抽取与分级 | 模型（调用 1） | 招聘信息文本 | Requirement 列表（JSON） |
| 2 引用核对 | 程序 | 招聘信息 + Requirement | 不是原文子串的 quote 标红 |
| 3 硬门槛检查 | 程序 | Requirement 中的 hard_type 与 params + 档案 | 五类硬门槛的 Match |
| 4 语义对照 | 模型（调用 2） | 非硬门槛的 Requirement + 档案 | 其余 Match（附档案证据原句） |
| 5 生成追问 | 程序挑选 + 模板 | 状态为“信息不足”的硬门槛和核心能力，以及档案矛盾 | 最多 3 个问题，硬门槛优先 |
| 6 回填答案 | 程序 | 用户回答 | 更新相关 Match |
| 7 结论判定 | 程序 | 全部 Match | 档位、理由、补救 |
| 8 准备清单 | 模型（调用 3，可与 4 合并） | 缺口列表 + 档案经历 | 简历改写句、作品建议、面试问题 |

提示词中的硬约束（沿用第二周方案）：不得虚构用户没有的技能或经历；每条判断引用招聘信息原句和档案原句；拿不准一律标“信息不足”，不得猜测；不输出百分比分数。

工程细节：使用 JSON 输出模式，程序校验字段，失败重试一次；温度设为 0；每份报告记录模型 ID，便于验证记录引用。

### 3.6 技术方案对比（D1）

| 方案 | 规则判定 | 档案复用 | 一页报告与对比 | 国内用户访问 | 学习成本 | 结论 |
|---|---|---|---|---|---|---|
| Streamlit + DeepSeek 接口 | 完全可控，Python 写 | SQLite + 账号登录 | 表格、勾选框、侧栏原生支持 | 需国内部署或本地运行 | 需要 1 人会基础 Python | **推荐** |

### 3.7 功能测试设计

测试集：20 份真实招聘信息（第二周已计划），覆盖 D4 确定的岗位类型，配 3 份不同的测试档案（强匹配、硬门槛不满足、核心能力缺口），共 60 组。每组由两名组员独立人工标注要求级别和结论，分歧讨论后定稿，并记录两人一致率（这个数字本身能说明“分级确实有难度”，支持 H1）。

| 指标 | 计算方法 | 第一版目标（待组内确认） |
|---|---|---|
| 硬门槛召回率 | 人工标的硬门槛中被系统识别的比例 | 90% 以上 |
| 分级一致率 | 系统级别与人工级别一致的比例 | 80% 以上 |
| 结论一致率 | 系统三档结论与人工结论一致的比例 | 80% 以上 |

## 4. 用户验证记录设计

### 4.1 三轮验证

| 轮次 | 时间 | 验证什么 | 方法 | 人数 |
|---|---|---|---|---|
| 第 1 轮：问题验证 | 第 3、4 周（现在） | H1 至 H5：问题是否真实、用户在意什么 | 按第二周提纲做访谈 | 同学 5 人以上、学长学姐 2 人、就业指导老师 1 人 |
| 第 2 轮：原型试用 | 第 5、6 周 | 能不能用、差异点用户在不在意 | 可用性测试（见 4.2） | 5 至 8 人，可与第 1 轮部分重叠 |
| 第 3 轮：改进复测 | 第 7 周以后 | 改动是否解决了第 2 轮的问题 | 同一任务复测 + 测试集重跑 | 3 至 5 人，至少 2 人是新面孔 |

做 5 至 8 人是因为可用性测试领域的常用经验：5 名左右测试者就能暴露大部分界面问题，再多收益递减。

### 4.2 原型试用的测试脚本

1. 请对方带一份自己真正感兴趣的招聘信息来（用真实岗位，不用我们准备的）。
2. 先让对方用自己平时的办法（通常是问 DeepSeek 或豆包）分析这个岗位，限时 10 分钟，组员记录用时和得到的结论。
3. 再让对方用原型完成同一任务，边做边说出想法（出声思考），组员只观察不帮忙，记录卡住的地方。为抵消先后顺序的影响，一半人先用原型、一半人先用通用模型。
4. 完成后问四个问题：
   - 这个岗位的硬门槛是什么？你缺哪几项？投递前要改简历的哪几句？（检验第二周定义的完成标准，能答对说明报告真的被看懂了）
   - 两种办法的结论一样吗？你更信哪个，为什么？
   - 报告里最有用和最没用的分别是哪一块？
   - 如果要看 5 个岗位，你会用哪个办法？
5. 结束后让对方给两种办法各打一个分（1 至 5 分，“我愿意按这个结果决定投不投”）。

付费意愿的观察（D5 主写个人付费，此项改为必做）：在缺口汇总和模拟面试入口标“会员功能”，另在报告页放一个“导出 PDF（会员功能）”按钮，点击只弹出说明，统计点击人数。这叫假门测试，比直接问“你愿不愿意付钱”更接近真实行为，但样本小，只能作参考。

## 9. 参考项目学习：秋招航海志

仓库：github.com/eel488888-cmyk/qiuzhao-voyage，作者署名“叫我小矩”，最近提交 2026-09-09，自述为群测候选版。

### 9.1 它是怎么做的

| 方面 | 做法 |
|---|---|
| 形态 | 纯前端网页（HTML、CSS、原生 JavaScript，约 7900 行），用启动脚本在本机开一个小网页服务，浏览器访问 |
| 存储 | 求职资料存在浏览器的 IndexedDB，密钥存 localStorage；没有账号和服务器 |
| 模型 | 用户自带密钥，支持 DeepSeek、OpenAI、Anthropic 和兼容接口；截图识别用视觉模型 |
| 模块 | 个人画像、投递管理（状态流转、日历、搜索）、岗位准备（匹配、自我介绍、开场白、行业研究、追问预测）、面试闪卡、面试复盘、游戏化、备份 |
| 提示词风格 | 每个功能一段系统提示 + 严格 JSON 模板；反复强调“禁止编造简历中没有的经历”“看不到的字段留空”“缺就说缺” |

### 9.2 值得学的五个做法

1. **JSON 三级兜底。** 先用 JSON 模式请求；解析失败就把原输出交给模型“只修格式、不改内容”；再失败就带着“上次格式错误”的提示重新生成；三次都失败才报错。这对演示稳定性很关键，已列为 F15。
2. **把模型输出拆成“先识别，再由人校对，再分析”。** 复盘功能先把面试记录拆成问答，让用户改正，再做分析，而不是一步到位。我们的简历导入（F16）和截图识别（F17）照此处理：识别结果先给用户确认，确认后才进入档案或分析。
3. **每条输出标注依据。** “基于简历”和“基于推断”分开标，与我们“附双方原句”的思路一致，已列为 F09。
4. **写清能力边界。** 复盘提示词要求模型声明“仅依据文字记录，无法判断语速、停顿、语气”。我们的报告也应写明“只依据你提供的档案和这份招聘信息，不了解公司内部的真实筛选标准”。
5. **招聘方意图的大白话解释。** 例如“良好的沟通能力”解释为“能不能把技术讲清楚给不懂技术的人听”。成本低，学生很需要，已列为 F03。

### 9.3 它没做、而我们要做的（写进竞品分析）

| 方面 | 秋招航海志 | 岗位筛选助手 |
|---|---|---|
| 投不投的结论 | 只给“投递策略建议”文字，由模型自由发挥 | 程序按规则判定三档，口径固定，可解释 |
| 硬门槛 | 不单独检查届别、到岗天数、实习时长等条件 | 五类硬门槛程序逐项检查 |
| 信息不足时 | 直接分析 | 先追问再下结论 |
| 原句核对 | 要求模型摘录原文，但不校验 | 程序校验引用是否真实存在 |
| 匹配表达 | 输出匹配百分比和能力雷达分数 | 不输出无依据数字 |
| 使用门槛 | 需要自己申请密钥、本机启动 | 打开链接即用 |
| 目标用户 | 秋招为主的全流程 | 实习和秋招中“这个岗位该不该投”这个决策点，再向后延伸 |

## 10. Vibe coding 工作方式

Vibe coding 是指用自然语言描述需求，由 AI 编程工具写代码，人负责运行、验收和提出修改。它能让不熟悉 Python 的组员做出原型，但有三个常见的坑：代码越改越乱、改好一处坏了另一处、没人说得清代码在做什么。课程最后要讲清楚产品怎么工作，所以下面几条要遵守。

### 10.1 准备（已定：Claude Code + GitHub）

- 建 GitHub 私有仓库，全组成员加为协作者。每人在自己电脑上克隆，用 Claude Code 在仓库目录里启动。
- 把本设计方案放进仓库 `docs/设计方案.md`，在仓库根目录放一份 `CLAUDE.md`（模板见 10.5）。Claude Code 每次启动都会自动读取它，相当于给 AI 的项目规矩，不用每次重复交代。
- 模型接口密钥放在 `.streamlit/secrets.toml`，并把这个文件写进 `.gitignore`，绝不提交到仓库。
- 提示词放在 `prompts/` 目录下的独立文本文件里，不写进 Python 代码。这样组员不懂代码也能改提示词，也避开了中文引号写进代码字符串导致语法错误的问题。

### 10.1.1 多人协作

- 每个功能编号开一个分支（如 `f05-hard-rules`），做完提交合并请求（Pull Request），由另一位组员在自己电脑上跑一遍再合并。这个审查记录本身也是“成员实际贡献”的证据。
- 同一时间不要两个人改同一个文件。`app.py` 最容易冲突，P0 阶段指定一人负责。

### 10.1.2 Claude Code 使用要点

- **一个功能一次对话。** 做完一个功能编号就 `/clear` 清空上下文再开始下一个，避免旧对话把它带偏。
- **先看计划再让它写。** 用计划模式（按 Shift+Tab 切换）让它先说打算改哪些文件、怎么改，确认没问题再执行。
- **改坏了就退回。** 每个能用的状态都提交一次；改乱了直接退回上一次提交，不要让 AI 在一团乱的代码上继续修。
- **让它跑测试。** 提示词里写明“改完运行 pytest，全部通过再告诉我”。

### 10.2 代码结构（让 AI 按这个结构写）

```
app.py              页面与流程（Streamlit）
rules.py            硬门槛检查、结论判定、风险关键词：纯函数，不调用模型
llm.py              模型调用、JSON 三级兜底
prompts/            提示词文本文件（组员可直接改）
models.py           数据结构（第 3.3 节）
storage.py          数据库读写（st.connection，本机 SQLite / 线上 Supabase）、用户与密码哈希、导出
tests/test_rules.py 规则的测试用例
data/               测试集与示例档案
```

把规则单独放进 `rules.py` 并写测试，是因为它是产品的核心差异，而且 AI 改别处代码时最容易顺手把它改坏。每次改动后运行测试，测试不过就不提交。

### 10.3 每一步怎么跟 AI 说

一次只做一个功能编号，提示词格式：

> 读 docs/设计方案.md 的 F05 和 3.4 节。在 rules.py 里实现五类硬门槛检查，输入是 Profile 和 Requirement 列表，输出 Match 列表。先写 tests/test_rules.py 的测试用例，覆盖“到岗 3 天对 4 天”“届别矛盾”“写着优先的实习时长”三种情况，再写实现，跑通测试。不要改其他文件。

验收三问：页面上能不能跑通？测试过没过？我能不能用一句话说清这段代码做了什么？第三问答不上来，就让 AI 解释到能答上为止，路演答辩时会被问到。

1. models.py 数据结构 + 示例档案和示例招聘信息
